# Direct3D 12 metadata migration

The staged removal moves the definitions from `d3d12.h`, `d3d12sdklayers.h`,
`d3d12shader.h`, and `d3d12compiler.h` out of `Windows.Win32.winmd`.
Their owner is `Microsoft.Direct3D.D3D12.winmd`, supplied by the
`Microsoft.Direct3D.D3D12` NuGet package at
`metadata\Microsoft.Direct3D.D3D12.winmd`. The namespace remains
`Windows.Win32.Graphics.Direct3D12`.

**Release blockers:** the currently selected SDK package does not contain this
file, and WinmdGenerator `0.71.25-preview` incorrectly emits inherited COM slots
when the bootstrap Windows metadata defines the SDK interfaces too. Before
merging or shipping the removal, publish and pin a WinmdGenerator containing the
reciprocal-reference fixes, generate and publish the SDK metadata with it, and
update `Direct3D12PackageVersion` in `Directory.Build.props`. Do not publish the
removal with metadata generated by the known-broken generator.

CsWin32 `0.3.367` also misclassifies external COM interfaces in struct fields.
For example, the migrated `DML_BUFFER_BINDING.Buffer` projects as a by-value
`ID3D12Resource` rather than the native `ID3D12Resource*`. Its metadata signature
is unchanged except for the assembly scope. A projection-tool fix and successful
paired-consumer validation are additional prerequisites; do not change correct
metadata or consumer pointer contracts to work around this error.

The coordinated [CsWin32 fix](https://github.com/microsoft/CsWin32/pull/1870) has
passed local reciprocal-reference tests and the unmodified consumer against the
actual generated pair. That validates the source fix, not an available package:
publication of a compatible CsWin32 release is still required.

There is a separate factory source-compatibility blocker: CsWin32 infers a
common namespace root for each metadata input. With SDK-only D3D12 metadata,
`D3D12CreateDevice` moves from `Windows.Win32.PInvoke` to
`Windows.Win32.Graphics.Direct3D12.PInvoke`, even though interface and struct
namespaces stay unchanged. The external COM fix does not address this, and
there is no existing supported projection-root override. Preserving factory
source compatibility requires a separate projection-root contract and
validation before release.

## Consumers

Projection tools must load both metadata files when generating Direct3D 12 or
Windows APIs whose signatures use Direct3D 12 types. The files reference each
other: Direct3D 12 uses common Windows types, and Windows interop APIs use
Direct3D 12 interfaces, enums, and structs. Do not combine the new SDK metadata
with an older Windows metadata package that still defines the same APIs.

The SDK package has no NuGet dependency on Windows metadata. Consumers explicitly
select compatible versions of both packages. The first Windows metadata package
that removes these definitions will expose
`WindowsWin32MetadataIncludesDirect3D12=false` from its `build` and
`buildTransitive` props. Missing or non-false values must be treated as
incompatible; do not infer compatibility from an unassigned version number.
This draft deliberately does not expose the capability property. Enable it only
after the fixed generator and projection tool are published, the SDK metadata is
published and pinned, and the released combination passes paired validation.

This migration does not remove common Direct3D, DXGI, shader cache registration,
Media Foundation's `d3d12video.h`, `mfd3d12.h`, Direct3D 11-on-12/9-on-12,
DirectML, or Holographic interop APIs.

## Building the staged removal

Build the tools, then supply the output of the SDK metadata generation:

```powershell
dotnet build BuildTools -c Release
dotnet build generation\WinSDK -c Release -t:EmitWinmd -p:D3D12MetadataPath=C:\artifacts\Microsoft.Direct3D.D3D12.winmd
```

`D3D12MetadataPath` defaults to the metadata path inside the selected SDK
package. A missing file is a build error, not a reason to silently restore the
old partition. The SDK metadata is a build-time emitter reference; it is not
copied into the Windows metadata package and its definitions are not emitted
again in Windows metadata.

The build removes the retired partition's stale generated `Direct3D12.cs`,
`Direct3D12.manual.cs`, and `Windows.Win32.Graphics.Direct3D12.constants.cs`
files so an incremental build cannot accidentally retain the old definitions.
The SDK winmd is also staged beside the Windows output for metadata inspection
and integrity tests, but is not included in the Windows NuGet package.

When inspecting a metadata file with external interface references, pass every
required metadata file explicitly to the delegate inspection commands:

```powershell
dotnet bin\Release\net10.0\WinmdUtils.dll showEmptyDelegates --winmd bin\Windows.Win32.winmd --reference bin\Microsoft.Direct3D.D3D12.winmd
dotnet bin\Release\net10.0\WinmdUtils.dll showPointersToDelegates --winmd bin\Windows.Win32.winmd --reference bin\Microsoft.Direct3D.D3D12.winmd
```

`--reference` accepts multiple paths. References supply type definitions for
resolution; findings are reported only for the file selected by `--winmd`.
Missing definitions remain errors. The Windows integrity tests supply the
staged SDK metadata automatically.

## Annotation ownership

D3D API annotations belong in the owning SDK headers. The move removes the
partition's array-size, COM output, optional-rectangle, return-value, and minimum
OS overrides from Windows generation. The SDK must preserve those annotations
and the two synthesized shader-component mapping constants before release.
Windows-owned video and interop annotations remain here.

Validation must establish unique ownership of the moved definitions, correct
SDK-scoped TypeRefs (including value-type signatures), complete COM inheritance
and vtable counts, and successful projection of both Windows interop and SDK
APIs using the actual two output files.
